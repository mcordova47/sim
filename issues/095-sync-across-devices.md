## Goal
Marc (2026-10-27): asked whether there is an issue for syncing across devices. There was none; the closest was a line in `docs/mobile.md` (section 12, question 10) that took "your save lives in this browser, with an export and import code only if a save is ever lost" as the default. Marc now wants to look at real cross-device sync (for example the phone and the laptop). **This issue is a design note first; nothing is built until Marc has read it.**

## Background
- The save is in the browser: `life.progress.v1` (apartment state, decor, deliveries, achievements and stats, encounters), `life.sound.v1` (settings, dialog voice, ad blocker), `life.tracks.v1` (made tracks), `life.flashcards.v1` (the sync key, the cap window, the guest mode) and the guest's cards (`life.flashcards.guest.es.v1`). An installed iPhone home-screen app has storage separate from Safari, so each starts empty. Safari can clear the storage of a site not visited for about seven days.
- The site is a static bundle on Netlify (auto-deploys from `mcordova47/sim`). The flashcards app already has a key-based progress endpoint and a pairing link or QR (`?pair=<key>`), which is a good model for the user experience: no accounts, a door key, not a password.
- The repo is public: no secret may be committed, and anything the game stores for players must be safe to expose.

## What the design note (`docs/sync.md`) must cover
1. **What syncs.** Each store above, and what does not (device-only things such as the touch layer, mute, the flashcards cap window, anything per-browser). The flashcards progress already syncs through its own key; say how the game's sync relates to it (one key for both, or separate) and the guest's local cards.
2. **Options, with costs and a recommendation:** (a) manual: export and import a save code or file (no server); (b) a small server in this repo: a Netlify Function with Netlify Blobs (or similar) storing one blob per random key, pairing by link or QR like the flashcards app; (c) reusing the flashcards app's progress endpoint for the game blob (needs changes in Marc's other repo, so surface them, do not make them); (d) browser-native sync (none that works across Safari and desktop reliably). Say what each needs, limits and free-tier costs, abuse risks (nothing limits the number of keys), and what can go wrong.
3. **Conflicts.** Two devices played since the last sync: a merge rule per kind of data (owned items and achievements and visited rooms as unions; counters and stats as the larger; the apartment state, clock and position as the newer or per field; decor placement; deliveries queue; made tracks by id), the order of operations on load, and what the player sees. Compare "newest save wins with a warning" (simple) with a field-wise merge (safer but more code); give a recommendation in the spirit of issue 089's "keep it small".
4. **The experience.** Pairing (a link, a code, a QR scan, as the flashcards app does), where the control lives (the pause screen), what is shown while syncing (nothing that adds pressure), failure and offline behaviour (the game must always work offline; sync is best effort), when it syncs (on load, on leaving or hiding the page, every few minutes).
5. **Privacy and safety.** What is stored on the server (an opaque blob), who can read it (anyone with the key), no personal data in the save, deletion, rate limits, size caps (the flashcards blob cap is 500 KB), and what the production build must not expose.
6. A staged build plan (smallest first, for example export and import first, then the server), a test plan, and the open questions for Marc with recommendations, ordered most important first so they can be asked one at a time.

  **Flaws found (the author should fix the note, no code):**
  1. **Made-tracks merge is not commutative/associative/idempotent and duplicates tracks.** The rule "same id, different text means two devices made different tracks; the other gets a fresh id" cannot tell an edit from a collision: `DemoStore.save` keeps the id and keeps `made` when a track is edited. Two-device case: A edits demo-1 (X to X2), B still has demo-1 = X. The merge keeps both, so every edit on one device leaves a stale copy on the other, and "older keeps its id" is a tie because `made` is unchanged. Re-merging a track already given a new id (Y at demo-2) with a device that still has Y at demo-1 mints a third copy (no dedupe by text is stated). Fresh ids depend on merge order: with a={1:X}, b={1:Y}, c={1:Z}, merge(merge(a,b),c) gives {1:X,2:Y,3:Z} and merge(a,merge(b,c)) gives {1:X,2:Z,3:Y}. So the property test in section 13 would fail for this row. Also a track deleted on one device comes back from the other (no tombstones), which contradicts "made things are never deleted" only in the sense that a deliberate delete is also undone, unmentioned. Needs a design that converges: ids that cannot collide (device or random suffix) plus a per-track revision or updated time (newer revision of the same id wins) plus tombstones (or an explicit decision that deleted tracks may return), and a stated dedupe rule.
  2. **A fresh device wins the "newer group".** The main use case is a new phone or an installed home-screen app that starts empty. Its `savedAt` is "the last local change", and a fresh device saves as soon as it loads or walks (the code saves on a timer and on hide, not only on change). It then beats the laptop's real play, and the world group (room, apartment variables, the `deliveries.hours` clock, encounter cooldown), `decor.placed` (the arranged room goes back to defaults, items stay owned but unplaced) and the prefs (ad blocker off, voice) come from an untouched game, while the toast says "Picked up where you left off". Same problem for an idle visible laptop whose clock keeps ticking. Needs: a defined `savedAt` (set only by a real player action, not by load, timer saves or merges; merged `savedAt` is the max of the inputs, never "now", otherwise idempotence and the "merged equals local" check in step 4 break), and a rule that a save with no real play (for example `deliveries.hours` 0 and no stats) loses to any played one; or choose the group winner by progress, not clock. Also say where `savedAt` is stored (nothing stores it today).
  3. **Epoch rule contradicts "import cannot lose anything" and "nothing is ever dropped".** (a) The larger epoch "wins whole", so importing an older file into a device that has reset (higher epoch) does nothing, which breaks the documented way to replace ("RESET PROGRESS, then import"); importing a file with a higher epoch into a played device discards the local progress silently. (b) Today's reset does not touch `life.tracks.v1`, prefs or the flashcards key, yet "takes it whole" would drop another device's made tracks (and prefs). Scope the epoch to what reset clears (progress, stats, achievements, decor, deliveries, encounters, guest cards on that device only), keep tracks and prefs merged, and make import ignore the epoch or ask. (c) section 2 says epoch is local only, "never in the blob", but section 2's document and section 7 put it in the blob: fix the table. (d) A silent loss of offline play on another device after a reset is a product choice with data loss: it should be a question for Marc (see below).
  4. **Preferences: a default can beat a choice.** "Newer side's value" for `adBlocker` and `dialogVoice` lets a fresh or untouched device's default override a deliberate choice (the loader treats a stored "beep" without `dialogVoiceChosen` as letters, so B's default `letters` with chosen=false overrides A's explicit beep, then chosen becomes true through the OR). Rule should be: a side that made a choice wins; only if both chose, the newer.
  5. **Deliveries row is under-specified.** Not stated: what happens when the same item is pending on both sides with different `at` (pick one deterministically, for example the earlier), or pending on one and waiting on the other (waiting wins). The union can exceed `DELIVERIES.maxQueued` (20); `parseDeliveries` silently drops the extras, so "no package is lost" is false at the cap and the fired milestone never retries. Two devices that each fired the same milestone before syncing can each queue a different item from a "first one you do not own" list, so a once-only gift gives two (harmless, say so). The rebase formula was checked for associativity in the simple cases and holds; it is the dedupe that is missing. Cosmetic: the kitchen `boxes` variable comes from the winner, so an item collected on the loser can leave the box stack flat. Say it is accepted.
  6. **How a merge is applied to the running game is not safe as written.** `Deliveries.load` and `Decor.load` replace everything, and `ProgressFeature.save()` rebuilds the stored save from in-memory objects. If the merge is written to storage but the world group is "held" until the next pause screen, the next timer save overwrites the stored merge with the old in-memory world. The note must say what the stored save holds while a change is held (for example the merge is applied to the in-memory objects at once except the world group, and a held world group is kept in memory and not written, or the whole apply waits), and that `Deliveries` needs a partial setter for the union parts. Say whether achievements that a merge unlocks show toasts.
  7. **Privacy and abuse claims to soften or fix.** "The function never logs a key ... nothing in logs" is not something the code can promise: the key is in the request path (`/api/sync/<key>`), and Netlify's own request and function logs, and any log drain, can record it. Say the function does not log it and that the platform may. `history.replaceState` changes the current entry but not the browser's global history or autocomplete, so "should not stay in history" is only partly true. A 32-character `[a-z0-9]` string check in `check-dist` will match hashes and ids in a minified bundle, so it needs a better test (for example only reject the dev-fake marker, or a known prefix). "No device info" is slightly off since the blob carries a random `device` id (fine, say it is random). A pasted pairing link in a chat is a lifetime credential: say that STOP SYNCING then TURN ON SYNC is the way to rotate (other devices see KEY NOT FOUND).
  8. **Key cap lockout.** An attacker (or bot with many IPs; 5 mints per hour per IP is not much) can fill the 1000 minted keys, and the 365-day sweep only removes old blobs, so new pairing could be off for a year. Cheap fix to write into the note: a minted key with no PUT expires in days (for example 7), only written blobs get 365. Also note each mint lists up to 1000 keys (cost unverified).

  **Real defects (fix in the note):**
  1. **`DemoStore.add` rename breaks "identity is the text".** The title is inside the `.track` text, and `names()`/`nameTaken` are case-insensitive over titles plus reserved names. A name clash means rewriting the title, so the stored text is no longer the text in the blob. Two devices each make a different "Foo": B adds A's as "Foo 2" (text X'), PUTs {X, Y, X'}; A then adds Y' and X' (it does not have X' so it is "new"), and so on: each track ends up twice, filling the cap of 12 and the blob's 36 with copies.
